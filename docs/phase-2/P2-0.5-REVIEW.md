# P2-0.5 第二阶段候选契约审查与冻结准备

审查日期：2026-11-07。结论：**通用技术约定可作为冻结候选；35 个 v0.2 操作及其业务语义尚不能冻结或启用。** 本报告只审查候选设计，不代表业务决策、数据库迁移或 API 实现。业务状态仅以 [P2_DECISIONS.md](../P2_DECISIONS.md) 为准：DEC-001 confirmed，DEC-002～DEC-014 pending。

审查依据：[API.md](../../contracts/API.md)、[openapi.json](../../contracts/openapi.json)、[Pydantic Schema](../../contracts/schemas.py)、[Mock](../../contracts/examples/README.md)、[P2-0 状态记录](P2-0.md)、现有 `server/app/models/`、`server/app/api/v1/` 与 Alembic 迁移。静态核对结果：API.md 的 35 组方法与路径和 OpenAPI 中 35 个 `proposed` 操作完全对应；OpenAPI 另保留 29 条 MVP 路径。11 组 Mock 文件可解析，但覆盖的是资源样例，不等于 35 个操作各自的可用请求与响应样例。

下文的「确定问题」指候选文档内部或前后端交接上的缺口；「待决策」指不能由后端单方定案的业务语义。优先级 P1 为冻结前必须处理，P2 为联调前应处理。

## 1. API 契约问题

| 优先级 | 性质 | 问题与证据 | 冻结前动作 |
| --- | --- | --- | --- |
| P1 | 确定问题 | 详情操作的 Mock `operation` 指向 `GET /.../{id}`，但 `empty` 为 `200 {"items":[],"next_cursor":null}`，是列表响应。例如 `examples/filing_packages.json`、`tax_profiles.json`、`tax_calculations.json`。OpenAPI 的详情成功响应是单对象。 | 为详情定义 404 `not_found`，把空列表样例绑定到对应列表操作；Mock 按方法与路径分别命名或标识。 |
| P1 | 确定问题 | API.md 为多个 GET/list 操作列出 `*_unavailable`、`import_not_parsed`、`settlement_pending` 等 409，同时空列表 Mock 使用 200。尚未区分「合法空结果」「资源不存在」「资源存在但前置条件不足」；OpenAPI 的 409 通用 `business_blocked` 样例也没有体现逐接口业务码。 | 制定逐操作的状态码/错误码矩阵：列表可为空则 200；未知或跨租户详情按既有安全边界 404；真正阻塞的动作才列 409，并让文档、OpenAPI 和 Mock 同步。 |
| P1 | 确定问题 | `If-Match` 被描述为目标版本字符串，但草稿/包审核需同时校验版本、哈希和数据版本；请求 Body 又含 `expected_*`。Header 的准确编码、强/弱 ETag、Header 与 Body 冲突时的错误、幂等重放遇到版本变化的优先顺序未定义。 | 定义一个可解析的条件令牌或明确逐操作的 `If-Match` 规则；规定 Body/Header 一致性、412/428/409 优先级及相同幂等键的重放结果。 |
| P1 | 确定问题 | `POST /studios/{studio_id}/tax-profiles` 的 Body 再次要求 `studio_id`；`POST /filing-tasks/{id}/platform-imports` 的 Body 再次要求 `filing_task_id`。两处均未说明不一致时如何处理。 | 去掉 Body 中重复 ID，或规定必须相等及统一 422/409 行为，并落实到 Schema/OpenAPI。 |
| P1 | 确定问题 | `ScopeCheckRequest` 输入所属期，但 `SupportedScopeRead` 没有适用起止日期；`FilingTaskRead` 固定 `scope_version` 却未固定档案修订版。范围与身份发生变化后，客户端无法判断任务绑定的精确快照。 | 增加范围适用期/修订引用与任务档案版本引用；适用性规则留给 DEC-002～007。 |
| P1 | 确定问题 | `TaxCalculationRun` 允许调用方给 `rule_versions` 和 `form_version`，而 `TaxCalculationRead` 不暴露规则键与版本的配对、输入快照摘要之外的参数/舍入依据。候选表设计承诺保存输入、公式、参数、舍入、中间值，但读取契约仅有 `key/amount_cents/ratio/formula/evidence`。 | 后端只能解析并校验已批准且适用的规则/表单版本；响应提供可审计的规则引用、输入版本和计算解释元数据，不预置具体税率。 |
| P1 | 确定问题 | `TaxFieldValue.value` 为任意字符串或 null，无法从 Schema 识别金额分、比率、日期、文本及其格式；与「金额整数分」通用约定缺少清晰的映射边界。 | 定义字段值的类型/单位判别和格式校验扩展点；具体字段键、含义和表单版本等 DEC-011。 |
| P2 | 确定问题 | `ScopeCheckRequest` 没有起止日期顺序校验；平台导入计数、文件大小、行号及金额整数范围没有完整约束。Pydantic 的 `StrictInt` 不限制 SQLite 整数上界。 | 给通用数值与日期范围补约束，并定义 422 校验错误实例；不触碰业务阈值。 |
| P2 | 确定问题 | 11 组 Mock 均有五类结果，但只覆盖 11 个读取操作；35 个操作中的创建、决策、审核、下载没有对应请求/响应样例。`forbidden` 有时示例为跨租户 404，有时应为全局动作 403，两者语义未分开。 | 按 35 个操作补全联调矩阵；将未认证 401、无全局权限 403、跨租户隐藏 404 分开。审批角色仍待 DEC-010/013。 |

`Idempotency-Key`、UTC 时间、UUID、整数分、Decimal 字符串、证据引用和版本字段已在三份候选契约中形成一致的通用方向。上述问题解决前，不应将具体 Header 语法、错误码矩阵或各资源状态转换标为冻结。

## 2. 数据模型问题

| 关系 | 已有设计的正确边界 | 需处理的问题与决策依赖 |
| --- | --- | --- |
| Studio ↔ MerchantTaxProfile | 档案以 `studio_id` 关联现有 Studio；档案 ID 稳定，修订表保存历史；未设「一个 Studio 一个主体」唯一约束。 | DEC-006 决定数量/归属；DEC-007 决定历史身份适用性。任务应固定所用档案修订，避免档案后来更新导致历史计算无法复现。税号的读取/脱敏受 DEC-010/013 约束。 |

| SettlementBatch ↔ PlatformRecord | 独立 `settlement_allocations` 可表达多对多，不改变 MVP `ReconciliationMatch` 语义。 | `SettlementAllocationRead` 只有记录 ID/金额，批次和收款来源版本、分配证据与核对公式未形成完整读模型。`settlement_receipts` 指向旧流水或新申报流水的模式由 DEC-009 决定；外部批次 ID 不可擅自设业务唯一约束。 |

| TaxCalculation ↔ TaxReturnDraft | 计算保存输入快照与哈希；草稿固定 `calculation_id`、数据/规则/表单版本，历史版本保留。 | 创建草稿须验证计算属于同一任务、已完成、未过期，且表单映射版本已审核。规则与表单需分别版本化；不能因草稿存在而推断税额或字段已可申报。具体规则/字段待 DEC-011。 |

## 4. Agent 集成问题与 DEC-014

后端/Agent 分工方向正确：AI 读取任务限域且经过授权的必要数据，提交 `AgentSuggestionEnvelope`、`AgentPolicySourceEnvelope`、`AgentPolicyRuleEnvelope` 等候选；后端用 Pydantic 和服务层核验归属、证据、版本、幂等，执行确定性结算/税务计算与持久化；AI 可以解释后端结果，不能写原始数据、确认分录、批准规则、改计算金额或发布资料包。身份/范围歧义、分类、政策/表单、草稿和资料包的关键决定需人工确认，具体确认人待 DEC-010/011/012。

冻结前需补足四个集成点：

1. `AgentSuggestionEnvelope` 外层的 `filing_task_id`、`source_task_id`、`data_version` 与内层每条建议的同名值缺少 Schema 层一致性约束；服务层校验虽有文字说明，但需要明确失败码和原子性。政策候选也需验证 source/rule 引用归属、版本与证据。
2. `PolicySourceSubmit` 的 `official_url` 只是字符串，来源真实性不能由格式验证替代；后端应保存抓取/审核证据，不让 AI 的解释自动成为规则。官方来源与批准门槛依 DEC-011。
3. MVP AgentTask/Run 和 WorkflowEvent 均绑定 `order_id`，P2 消息使用 `filing_task_id`；候选辅助表提到 `filing_agent_tasks/runs/events`，但调用请求/回执、运行 ID、检查点、重试幂等键和任务进度读取尚无统一契约。`schema_version="2.0"` 不能直接替换 MVP `1.0`。
4. DEC-014 的问题是 **进程内调用或独立服务的运行边界**。目前没有实测的 Python 3.11 兼容性、依赖隔离、故障/超时和重试数据，故本报告不选择任一部署方案。先冻结与部署无关的请求/结果 Schema、授权与审计要求，再由负责人确认运行边界；任何 Agent 依赖不得迫使 `server/` 升级 Python。

## 6. 建议修改项与审查顺序

1. **先修契约自洽性**：按操作重建 Mock；统一 200/401/403/404/409/412/422/428/503 语义；定义 `If-Match`、幂等键与 Body 预期版本的一致性；解决路径与 Body 重复 ID。同步修改 API.md、OpenAPI、Schema、Mock，并用静态校验对比 35 个操作。
2. **补齐跨资源读写链路**：提供文件和政策来源受权读取、材料/导入诊断、任务进度与审批历史的候选契约；对结算到账、分录修订、包预览/撤回只列方案，不在对应 DEC confirmed 前定案。
3. **明确版本与证据链**：任务固定档案修订；规则固定来源版本/哈希；计算返回审计所需的规则键、参数、舍入及输入版本；草稿字段用类型化值；包 manifest 和审批动作使用结构化引用。具体政策与表单内容仍保持空白。
4. **联合评审**：负责人确认 DEC-002～014 的受影响条目；前端核对每个操作的页面读写和错误状态；AI 核对内部候选消息、证据和运行边界；后端据确认结果更新单一候选版本。未确认的业务操作继续保持 `proposed`。

## 7. 可以冻结的通用技术约定

- 后端 Python 固定 3.11；FastAPI、Pydantic 2、SQLite、SQLAlchemy 2、Alembic；测试使用 Python 3.11。若 Agent 依赖不兼容，应隔离运行，不能改后端版本。
- 原 MVP 29 条路径、订单/文件/Agent/事件/报告模型与权限边界保持兼容；新 FilingTask 独立于 Order。新增数据库结构只通过 Alembic 增量迁移。
- 新资源统一小写 UUID JSON 字符串；金额为整数分、比率为 Decimal 字符串；日期 ISO 日期、时间为 UTC；原始数据不可覆盖，派生数据保留来源和证据引用。
- 数据、规则、表单、草稿、资料包分别保留版本；过期结果与过期审批不能作为发布依据。关键写入有幂等和条件版本校验，具体令牌编码仍需修订。
- 新 API 继续使用 `/api/v1`，保持既有错误外形与租户隔离；提议接口必须明确标记 `proposed`，未挂载前不能宣称可调用。

## 8. 不能冻结的业务约定

首发地区、经营主体、纳税人身份、申报事项、所属期、平台与格式；Studio 与税务主体数量、历史身份适用、任务唯一性；资金来源/去重/结算公式；分类/政策/草稿/资料包审批权；税率、优惠、政策参数、表单字段与官方来源；资料包格式、发布/撤回和历史访问；生产角色与 Agent 部署形态。候选状态枚举及其转换、逐资源可见性也不能视为已批准业务规则。

**审查结论：**保留 P2-0 候选状态，不启动 BE2-01 的业务模型/迁移。项目负责人、前端、AI、后端审阅上述问题并在决策登记表完成相应确认后，再修订和冻结接口契约。本轮没有更改任何决策状态、挂载路由或实现业务功能。
