# 第二阶段：AI 开发计划

**LedgerCrew · 账清社｜MVP 验收后启动｜角色：AI 开发**

前置计划：[MVP AI 任务](../AI.md) · [MVP 公共约定](../PLAN.md)。

## 阶段目标与启动条件

在 MVP 的五个角色和基础工作流上，扩展财税运营总管及八个专业 Agent，形成材料收集、结算核对、账务分类、政策研究、税务计算、风险审计和申报资料交付的完整协作链。

本文件是第二阶段计划。MVP 的真实调用、交接、人工等待和恢复验证通过后启动；按里程碑推进，不计入原 MVP 的 40 小时排期。继续使用 MiMo 与 Microsoft Agent Framework，代码归属 `server/app/agents/`，样例归属 `fixtures/`。

首个样例限定一个地区、一类经营主体、一种申报事项和一个平台数据格式。启动时与前后端共同锁定场景，AI 成员查证官方政策和表单，后端记录支持范围及数据契约。相关税务规则尚未验证时，明确标记待确认。

## 角色与职责

共 **一个总管＋八个专业 Agent**，角色可在同一进程中运行，按任务建立独立指令、上下文、工具与结构化结果。

| 角色 | 职责与交接结果 |
| --- | --- |
| 财税运营总管 | 分解服务任务、调度节点、追踪结果、升级异常，向老板请求关键决定 |
| 客户服务 Agent | 接单、核实商户资料、补充材料、整理询问草稿 |
| 票据识别 Agent | 提取票据及费用凭证，保留来源并标记未知字段 |
| 经营数据 Agent | 解析平台记录，调用结算与到账核对工具，整理差额 |
| 会计处理 Agent | 根据经营事实提出收支分类和科目建议，交由人工确认 |
| 政策研究 Agent | 获取官方规则、识别适用条件与有效期、提出规则候选 |
| 税务计算 Agent | 检查输入并调用后端确定性计算工具，解释计算结果 |
| 风险审计 Agent | 核对缺失、矛盾、证据、规则适用及表间校验结果，列出阻塞与待确认项 |
| 交付运营 Agent | 组织申报草稿说明、材料清单、报告和办理提醒，交人工审核后发布 |

## 任务清单

- [ ] **AI2-01｜角色与扩展工作流。** 复用 MVP 的有效节点，新增会计、政策、税务和审计职责，使用 `WorkflowBuilder` 串联输入检查、专业任务、人工待办和交付。**验收：** 每次交接有真实结构化成果、引用和下一动作；老板批准仍由后端校验。
- [ ] **AI2-02｜平台数据与凭证理解。** 适配首个平台实际导出格式，提取订单、退款、佣金、营销费、补贴和结算标识，结合票据识别补全候选关联。对账与批次汇总调用后端工具。**验收：** 能解释应到账、实际到账、在途和差额；多笔同金额不会仅凭模型判断强行关联。
- [ ] **AI2-03｜会计处理建议。** 依据已核对业务提出收支分类与科目建议，关联凭证和解释，识别内部转账与净到账口径。人工纠正后保存修订并触发受影响计算更新。**验收：** 原始记录不被覆盖；低依据和冲突进入人工待办，模型建议不会直接成为未经确认的申报依据。
- [ ] **AI2-04｜官方政策检索。** 从国家税务总局、相关地方税务机关等官方公开页面获取首个场景需要的政策、表单和填报说明。记录标题、机关、URL、发布与生效信息、适用地区／主体／所属期、抓取时间和快照。提供来源变化检测及不可获取时的待处理状态。**验收：** 每条候选规则可追溯；来源受登录或其他访问限制时，支持人工导入官方材料并保留来源记录。
- [ ] **AI2-05｜规则提取与适用判断。** 将官方资料整理成有版本、来源和适用条件的结构化候选，区分税务申报、财务报表和工商年报，识别新旧文件及冲突。与后端共同确认规则参数和表单映射。**验收：** 只有经人工确认并由后端启用的规则用于计算；按业务所属期判断适用性，未知和冲突不自行定案。
- [ ] **AI2-06｜税务工具与字段追溯。** 为税务计算 Agent 接入后端计算、表单映射和校验工具，返回输入快照、计算过程、规则版本和字段依据。模型解释结果并形成待补清单。**验收：** 税额来自代码；缺少身份、材料、规则或字段时形成明确阻塞，不编造税率、数字或默认零值。
- [ ] **AI2-07｜风险审计与人工决定。** 检查票据、平台结算、账务分类、适用规则、计算和申报字段之间的证据与一致性，将问题分成阻塞项及可说明的待确认项。通过已有审批与检查点机制恢复执行。**验收：** 输入或规则变化后重新计算与审核；关键问题未解决时不能批准完整申报材料交付。
- [ ] **AI2-08｜资料包与交付说明。** 根据服务端确认的草稿、明细和规则组织申报说明、异常、材料清单与办理提醒，保留证据引用和版本。具体周期来自对应事项规则。**验收：** 客户能理解收到什么、缺什么和下一步如何办理；交付文案不把草稿或站内审核表述成税务机关受理。
- [ ] **AI2-09｜样例、失败与回归。** 增加平台扣费退款、合并／拆分结算、跨期、内部转账、规则版本切换、缺失身份、缺失证据、错误分类、舍入和审批恢复样例，给出人工核实的预期结果。**验收：** 真实 MiMo 验证通过；错误能阻塞或转人工，旧 MVP 样例保持通过，记录模型用量与局限。

## 需要与队友对齐

- **后端提供：** 商户档案、规范化平台数据、账务与证据、版本化政策、确定性计算与字段校验、申报状态、人工审批及资料包接口。复用共享 Pydantic 类型。
- **AI 提供：** 官方来源与规则候选、独立角色、工作流工厂与节点、结构化输出、真实事件、人工待办说明以及测试样例。
- **前端展示：** 专业角色与工作进度、分类建议、适用政策、申报字段来源、阻塞问题和最终交付；统一经后端输出。
- **共同确认：** AI 检索与解释、代码计算与校验、人类确认适用规则与关键事项的分工。各角色工具权限和最终发布由业务层约束。

## 里程碑与交付

| 里程碑 | AI 交付 | 依赖 |
| --- | --- | --- |
| P2-0：范围与契约 | 首个场景的官方来源、表单说明及共享结果样例 | 三人确认目标，后端定义字段和范围记录 |
| P2-1：数据与账务 | 平台解析、经营数据和会计处理节点 | 后端导入与核对工具，前端确认体验 |
| P2-2：申报草稿 | 规则研究、税务工具调用、字段追溯和审计 | 已确认规则与后端计算／映射 |
| P2-3：交付与回归 | 资料包说明、真实样例、失败恢复和 MVP 回归 | 后端版本审批与发布；前端完整流程 |

交付物：角色指令与工作流、工具封装、来源可追溯的规则候选、首个事项的完整样例、回归结果及运行证据。全国规则覆盖和多平台逐步扩展；代账价格、办理频次和漏报原因通过实际访谈验证。
