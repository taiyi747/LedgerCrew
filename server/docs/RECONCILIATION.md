# 第四阶段：确定性对账

本模块仅使用 Python 规则和整数分，不调用 OCR、Agent 或大模型。`InvoiceRecord` 是未来票据处理集成的结构化输入；原始图片仍由 `UploadedFile` 保存。当前没有公开的发票写入 HTTP 接口，也不包含 Agent 实现。集成方在授权与来源校验后，可使用 `InvoiceRecordCreate` 与 `reconciliation_service.persist_invoice(session, order_id, data)` 写入，随后提交事务。输入必须引用同一订单内校验为 `valid` 的 `invoice_image` 文件；金额为整数分，不接受浮点数。提取状态为 `ready`、`needs_review` 或 `invalid`。只有 `ready` 且必要字段完整的票据可自动匹配。

## 匹配规则

工作室、购买方、销售方和流水交易方统一做 Unicode NFKC、空白折叠和大小写折叠，不做模糊推断。工作室仅为购买方时，方向为 `OUT`，交易方为销售方；仅为销售方时，方向为 `IN`，交易方为购买方。两侧都匹配或都不匹配工作室名称，产生 `COUNTERPARTY_OR_DATE_CONFLICT`。

只有票据和流水日期均在订单账期内，且交易方、方向、整数分金额相同、日期相差不超过 3 天时，才构成候选。**票据与流水两侧都恰好只有一个候选**时才自动匹配；多候选不分配。每个批次通过数据库唯一约束确保每张票据和每条流水最多匹配一次。不执行一对多、多对一或跨期核销。

重复票据优先以规范化后的发票号码识别；无号码时以来源图片 SHA256 识别。重复流水优先以 `external_id` 识别；无编号时要求日期、规范化交易方、方向、金额和描述均完全相同。重复记录保留在数据库，生成独立工单，并退出自动匹配。

未匹配票据依次检查同交易方、同方向、3 天内的金额差异，再检查同金额的方向或日期冲突，最后记录缺少流水。多个金额冲突候选生成 `MULTIPLE_CANDIDATES`，不会选一个。未被匹配或其他冲突引用的流水生成 `MISSING_INVOICE`。字段缺失或提取状态非 `ready` 生成 `INVOICE_FIELD_MISSING`。重复、跨期和身份不明确也生成独立工单；工单初始状态均为 `open`，本阶段没有审批或状态变更接口。

## 批次与汇总

`POST /api/v1/orders/{order_id}/reconciliation/run` 创建新批次，保留旧批次。`GET /api/v1/orders/{order_id}/reconciliation`、`/matches` 和 `/exceptions` 返回最新批次的数据。未运行时这些 GET 返回 404。所有接口按现有订单归属做权限检查。

收支只统计**流水日期在订单账期内**的导入记录。收入为 `IN` 金额之和，支出为 `OUT` 金额之和，净资金变动 = 收入 − 支出。重复流水仍计入原始流水总额，同时单独标为异常，避免暗中修改导入金额。`matched_count` 为匹配对数；`unmatched_count` 为未参与匹配的票据数加流水数（含重复和跨期记录）；`exception_count` 为本批次工单数。净资金变动不等于会计利润或应税所得。

每次运行原子性写入批次、匹配、工单、工作流事件和审计记录。证据 JSON 保存明确规则依据、候选 ID 和差异，不覆盖原始票据、流水或旧批次。`match_rule` 当前为 `exact_party_direction_amount_date_3d_unique_v1`。

## 待确认事项

- 同一账期多份银行流水存在重复记录时，面向客户的经营概览是否需要额外展示“剔除重复后的试算值”；当前 API 严格按全部导入流水计算，并把重复另列工单。
- 票据 `amount_cents + tax_cents` 与 `total_amount_cents` 不一致时的人工复核规则，以及开票号码的正式唯一范围。当前不猜测税额关系，匹配只使用票据总额。
- 未来 Agent 或人工写入票据时的认证、权限和版本修订流程。当前仅提供受校验的服务入口，不开放客户写入接口。
